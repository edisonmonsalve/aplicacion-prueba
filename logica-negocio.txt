LOGICA DE NEGOCIO REAL DE LA APLICACION (estado actual del codigo)

Este documento describe el comportamiento real implementado en el servidor, no aspiraciones.
Cada regla indica si esta implementada (OK), parcialmente (PARCIAL) o pendiente (PENDIENTE).

============================================================
1. ENTIDADES Y DATOS
============================================================

Usuario: nombre, correo, contrasena cifrada (bcrypt), rol (admin, contador, operador, consulta), estado (activo/inactivo), fecha de creacion.
Categoria: nombre y estado, con productos asociados.
Producto: SKU, nombre, categoría, precio, costo, stock actual, stock mínimo, estado.
Movimiento de stock: producto, usuario, tipo (entrada/salida), origen (compra/venta/entrega/merma/ajuste), cantidad, costo unitario, motivo, fecha.
Cotizacion: cliente (nombre, documento, email), fecha de validez, estado, lineas, totales, historial de estados, auditoria.
Presupuesto: nombre, tipo de periodo (dia/semana/mes/anio), rango de fechas, meta de ingresos, alerta (%), estado, lineas.
Transaccion financiera: tipo (ingreso/gasto), monto, fecha, categoria financiera, cuenta, producto/cotizacion/movimiento asociado, descripcion, anulada_de.
Cuenta financiera: nombre, tipo, saldo inicial, ingresos, egresos, saldo actual, estado.
Categoria financiera: nombre, tipo (ingreso/gasto), estado, contadores.

============================================================
2. AUTENTICACION Y ROLES
============================================================

OK  Login con correo y contrasena, emite JWT (8h) con {id, rol}.
OK  Roles: admin, contador, operador, consulta.
OK  Permisos validados en servidor (middleware auth), no solo en UI.
OK  Admin: gestiona usuarios, inventario, cotizaciones, finanzas.
OK  Contador: gestiona finanzas (lectura de inventario/cotizaciones).
OK  Operador: registra productos, movimientos, cotizaciones (lectura de finanzas).
OK  Consulta: solo lectura.
OK  Un usuario no puede desactivarse a si mismo ni quitarse el rol de admin.
OK  No se puede desactivar ni quitar rol al ultimo administrador activo.
OK  Cambio de contrasena requiere contrasena actual.
PARCIAL  Email duplicado en updateUser se convierte en 409 (implementado); en createUser depende del manejo del error de constraint.
PENDIENTE  Comparacion de correos sin distinguir mayusculas/minusculas (no normalizado).

============================================================
3. INVENTARIO
============================================================

OK  SKU y correo unicos (constraint de BD).
OK  Precio y cantidad deben ser mayores que cero (validacion Zod).
OK  Salida rechazada si la cantidad supera el stock disponible.
OK  Movimiento y actualizacion de stock son atomicos (transaccion + FOR UPDATE).
OK  Producto inactivo no admite movimientos.
OK  Borrado logico: desactivar en vez de eliminar si tiene movimientos.
OK  No eliminar categoria con productos asociados.
OK  No desactivar producto con stock disponible ni si esta en cotizaciones enviadas/aprobadas.
OK  Stock inicial con entrada inicial: PARCIAL (el sistema no crea automaticamente una entrada inicial al crear producto con stock; stock_actual se guarda directamente). Pendiente de implementar para trazabilidad completa.
OK  stock_actual se guarda en el producto y se actualiza en la misma transaccion del movimiento.

============================================================
4. COTIZACIONES
============================================================

OK  Estados: borrador, enviado, aprobado, entregado, rechazado, vencido.
OK  Solo se editan cotizaciones en borrador.
OK  El precio se toma del catalogo (servidor es autoridad).
OK  Un producto no puede repetirse en las lineas de una cotizacion.
OK  Descuentos mayores al limite requieren rol admin.
OK  No se puede aprobar una cotizacion vencida.
OK  No se puede entregar una cotizacion vencida.
OK  Entregar descuenta el stock de cada linea (FOR UPDATE, ordenado por id) y genera el ingreso en finanzas.
OK  Si falla el stock, se informa que productos fallan sin mover nada (validacion previa).
OK  Duplicar crea un nuevo borrador con las mismas lineas (lectura + creacion en transaccion).
OK  Historial de estados y auditoria de cotizaciones.
PARCIAL  Rechazar una cotizacion vencida esta permitido (decision de negocio pendiente).
PARCIAL  buildLines usa FOR UPDATE (implementado). Lectura en duplicateQuote envuelta en transaccion (implementado).
PENDIENTE  Productos inactivos se bloquean al construir lineas (implementado), pero un toggle concurrente puede dejar datos obsoletos (mitigado con FOR UPDATE).

============================================================
5. PRESUPUESTOS
============================================================

OK  Estados: borrador, activo, cerrado.
OK  Solo se editan presupuestos en borrador.
OK  Solo un presupuesto activo por periodo (solapamiento de fechas bloqueado).
OK  Activar bloquea si ya existe un presupuesto activo solapado.
OK  Cerrar impide nuevas transacciones en el periodo.
OK  Lineas validadas por categoria financiera y monto mayor que cero.
PARCIAL  No mezclar lineas generales y por producto en la misma categoria: es recomendacion documentada, no validada por servidor.
OK  Disponibilidad calculada por presupuesto activo cuyo rango contenga la fecha, sin limite arbitrario, prefiriendo el mas especifico y la linea del producto.
OK  Auditoria de presupuestos (crear, editar, activar, cerrar, eliminar).

============================================================
6. TRANSACCIONES FINANCIERAS
============================================================

OK  Ingreso suma capital, gasto lo reduce.
OK  No se editan ni se borran: se anulan con una contrapartida del mismo importe.
OK  Una transaccion de anulacion no se puede anular.
OK  Las transacciones automaticas (origen stock o cotizacion) no se anulan manualmente.
OK  Un periodo cerrado no admite transacciones.
OK  El capital disponible se calcula solo con cuentas activas.
OK  El resumen excluye asientos anulados.
OK  Auditoria de transacciones (crear, anular).
PARCIAL  Revertir un asiento automatico no revierte stock ni cotizacion (bloqueado por ahora).

============================================================
7. MOVIMIENTOS DE STOCK Y FINANZAS
============================================================

OK  Una entrada con costo y origen="compra" genera automaticamente el egreso real de la compra en finanzas (gasto "Compra de inventario").
OK  Una salida con origen="venta" genera un ingreso en finanzas (ingreso "Ventas") por precio × cantidad.
OK  Salidas con origen="entrega/merma/ajuste" actualizan solo stock, sin asiento financiero.
OK  El origen es obligatorio en todos los movimientos y se valida en el servicio (entrada → compra/ajuste; salida → venta/entrega/merma/ajuste).
OK  El costo unitario en entradas con origen="compra" actualiza el costo del producto al confirmar factura compra.
OK  Movimientos con costo cero: se permiten pero no generan asiento financiero (por diseno).
OK  El origen determina si se genera asiento financiero automático o solo movimiento de stock.

OK  Bloquear productos con FOR UPDATE al construir lineas de cotizacion.

12. MODULO DE FACTURACIÓN
============================================================

OK  Facturas con tipo "venta" (FAC-0001) y "compra" (COM-0001), numeración consecutiva por tipo.
OK  Cabecera: tipo, fecha, contraparte, documento, email, estado (borrador/confirmada/anulada), total, notas.

OK  Listado con filtros por tipo, estado, fecha y contraparte; detalle con totales de líneas.

============================================================
13. NOTAS DE DISEÑO
============================================================

- stock_actual se guarda en el producto para consulta rapida; los movimientos son el historial.
- Los permisos se validan en servidor, no solo en la UI.
- Las operaciones criticas usan transacciones y bloqueos (FOR UPDATE).
- Los asientos automaticos son idempotentes gracias a indices unicos.
- El sistema prioriza consistencia sobre conveniencia en operaciones financieras.
- El módulo de facturación usa numeración consecutiva por tipo (FAC/COM) para trazabilidad.
- Las facturas de compra actualizan tanto stock como costo unitario del producto.
- El campo `origen` en stock_movements es la fuente única de verdad para distinguir compras, ventas y ajustes.
